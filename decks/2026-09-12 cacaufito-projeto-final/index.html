Duas Formas de Especificar Antes de Codificar

OpenSpec entrega rastreabilidade; Spec Kit entrega priorização

OpenSpec

Delta-driven: ADDED / MODIFIED / REMOVED

  • Rastreia exatamente o que mudou num requisito existente
  • Sincronização obrigatória com a spec principal
  • Usado no modelo, histórico, incerteza e mais 4 mudanças

GitHub Spec Kit

User-story-driven: P1 / P2 / P3

  • MVP explícito desde o planejamento
  • Checklist de qualidade da spec, autovalidado
  • Usado na feature de estatísticas agregadas

O Contrato que o Código Tem que Cumprir

Cenário Given/When/Then real, escrito antes de qualquer linha de implementação

spec.md 
#### Scenario: Close call between top classes flagged as uncertain
- **WHEN** the difference between the top two classes'
  probabilities is below the documented close-call margin,
  even if the top confidence itself is above the
  low-confidence threshold
- **THEN** the response includes `is_uncertain: true` and
  `uncertainty_reason: "close_call"`
// openspec/specs/leaf-inference-service/spec.md — caso de borda real

Autonomia Sim, Cheque em Branco Não

Dois pontos de parada obrigatórios, não negociáveis

Nenhum endpoint novo vai para main sem revisão humana explícita do diff, mesmo com testes automatizados passando

Ações destrutivas e leitura de segredos são bloqueadas estruturalmente, não só combinadas verbalmente

Toda mudança nasce de uma spec revisável, antes de qualquer código ser escrito

O Bug Que Só Apareceu Testando de Verdade

Um botão "Carregar mais" continuava visível mesmo quando a lista estava vazia, mesmo tendo o atributo HTML hidden. Lendo o código isso parecia correto; só apareceu de verdade testando no navegador (Playwright).

css 
/* a regra do botão vencia o [hidden] do navegador: */
.btn { display: inline-flex; }  // especificidade > [hidden]

/* correção: forçar o [hidden] a sempre vencer */
[hidden] { display: none !important; }
// frontend/static/style.css — correção real aplicada
